## Вопрос 1. Сопровождение и развёртывание в жизненном цикле. Задачи менеджера сопровождения

Развёртывание — доставка, установка, настройка и ввод версии в целевую среду. Сопровождение — действия по поддержанию работоспособности ПО после ввода: исправление ошибок, адаптация к изменению среды, улучшение характеристик и предотвращение потенциальных проблем. Развёртывание отвечает на вопрос «как безопасно запустить релиз», сопровождение — «как обеспечить его дальнейшую работу».

Различают корректирующее сопровождение (устранение дефектов), адаптивное (новая версия ОС или интерфейса), совершенствующее (повышение удобства и производительности), профилактическое (обновление зависимостей, устранение технического долга). Сопровождение использует журналы событий, систему заявок, мониторинг, резервные копии, регламенты инцидентов и релизов.

Менеджер сопровождения организует приём и классификацию обращений, расставляет приоритеты по влиянию и срочности, назначает ответственных, следит за сроками и SLA, согласует исправления и обновления. Он обеспечивает сбор информации для воспроизведения дефектов, управление изменениями и конфигурациями, проверку новых версий, коммуникацию с пользователями и документацию. После критического сбоя организуется анализ первопричин и предупреждающие меры.

После выпуска программы возникают обращения пользователей и новые требования. Инцидент — уже произошедшее нарушение работы; проблема — причина одного или нескольких инцидентов; изменение — согласованное вмешательство в систему. Менеджер сопровождения не обязан лично исправлять каждую ошибку: он организует диагностику, назначает исполнителя, определяет приоритет, согласует выпуск исправления и информирует заказчика. Для срочных инцидентов важен план возврата к работоспособной версии. После устранения ошибки выполняют повторную проверку, чтобы похожая проблема не возникла снова. Сопровождение отличается от эксплуатации: эксплуатация означает повседневное использование, а сопровождение — обеспечение пригодности программы и её развитие после поставки.

Пример: после обновления приложение перестало отправлять письма. Менеджер подтверждает инцидент, оценивает влияние, организует откат либо исправление, контролирует восстановление и выпуск отчёта. Критерии успешного сопровождения — доступность, время восстановления, число повторных инцидентов и удовлетворённость пользователей.

## Вопрос 2. Подготовка Python-сервиса к контейнеризации. Настройка через переменные окружения

Контейнеризация упаковывает приложение с зависимостями в изолированный образ, который запускается на совместимом контейнерном движке. Для Python-сервиса готовят явный список зависимостей, точку входа, конфигурацию, проверку здоровья и корректное завершение процесса. В Dockerfile обычно указывают базовый Python-образ, рабочий каталог, копирование файлов, установку зависимостей и команду запуска.

Переменные окружения отделяют конфигурацию среды от кода. Например, APP_PORT, LOG_LEVEL, DATABASE_URL, DEBUG считывают через os.getenv(). Значения преобразуют к нужному типу и проверяют; DEBUG="false" как непустая строка всё равно истинно, если использовать просто bool(). Порт сервиса должен соответствовать фактическому порту, на котором он слушает, и опубликованному порту контейнера.

Пример: port = int(os.getenv("APP_PORT", "8000")); запуск — python app.py или gunicorn ... для подходящих веб-фреймворков. Файл .dockerignore исключает .venv, .git, тестовые результаты и секреты из контекста сборки. Пароли и токены не вшивают в образ; при необходимости используют секреты Docker или защищённое хранилище. В контейнере желательно запускать процесс не от root.

Контейнерный образ собирается один раз, а разные запуски получают настройки через окружение. Например, на тестовом сервере можно задать DEBUG=false и APP_PORT=8000, а на рабочем — другие значения без изменения исходного кода. Переменная окружения приходит в Python как текст, поэтому номер порта преобразуют через int(). Ошибку в значении следует обнаружить при запуске. Файл Dockerfile содержит шаги сборки образа; docker run создаёт контейнер, то есть работающий экземпляр образа. Контейнер не заменяет резервное копирование: данные, записанные только внутрь удаляемого контейнера, могут пропасть. Поэтому постоянные файлы и базы хранят в отдельных томах или внешних сервисах.

Проверка: сборка docker build -t my-service ., запуск docker run --rm -p 8000:8000 -e APP_PORT=8000 my-service, затем HTTP-запрос к /health. Вывод: один образ переносим между средами, различия задаются конфигурацией.

## Практическое задание. Поиск товара по названию

Условие (по скану преподавателя). Товары A1 — белые кеды, A2 — зимние ботинки, A3 — чёрные кеды. Один ввод фрагмента названия, поиск по подстроке без учёта регистра. Пустая строка показывает все товары; если ничего не найдено — «Товары не найдены». Каталог не изменять.

### Как объяснить код преподавателю

lower() переводит и запрос, и название в нижний регистр. Цикл for проверяет каждый товар; выражение query in name означает вхождение части текста. Пустая строка входит в любую строку.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.

### Проверь себя

Ввод: КЕДЫ   →   Ожидается: A1 и A3

Ввод: пустая строка   →   Ожидается: Все три товара

Ввод: туфли   →   Ожидается: Товары не найдены
