## Вопрос 1. Надёжность, питание и охлаждение. Методика выбора аппаратно-программной платформы

Надёжность платформы — способность выполнять требуемые функции в заданных условиях в течение времени. На неё влияют качество компонентов, температурный режим, электропитание, резервирование, мониторинг и процедуры обслуживания. Оценивают доступность, частоту отказов, MTBF/MTTR там, где их применимость обоснована, а также риски потери данных и время восстановления.

Питание: качественные блоки питания, ИБП/UPS, защита от скачков, мониторинг энергопотребления. Для критичных серверов возможны резервные блоки питания и независимые линии. Охлаждение: подходящая вентиляция, чистые радиаторы, корректный воздушный поток, контроль температур CPU/GPU/дисков и запаса по тепловыделению. Перегрев приводит к троттлингу, нестабильности и сокращению срока службы.

Методика выбора: 1) определить задачи и нагрузку (число пользователей, объём данных, CPU/GPU, IOPS); 2) установить требования к доступности, совместимости и безопасности; 3) оценить ОС, драйверы, версии ПО и возможность виртуализации; 4) определить запас ресурсов и расширяемость; 5) рассчитать общую стоимость владения (оборудование, лицензии, энергия, обслуживание); 6) протестировать пилот; 7) задокументировать выбор и риски. Нельзя выбирать только по максимальной мощности или минимальной цене.

Надёжность платформы зависит не только от мощности процессора, но и от качественного питания, охлаждения, дисков, сети и наличия резервирования. Перегрев вызывает снижение производительности и иногда аварийное выключение; нестабильное питание может повредить данные. Для критичных систем применяют ИБП, мониторинг температуры, резервные блоки питания и проверенные процедуры восстановления. Подбор начинают с нагрузки и требований: количество пользователей, объём данных, допустимое время простоя, бюджет, условия помещения и возможность расширения. Затем сравнивают варианты по производительности, совместимости, обслуживаемости и общей стоимости владения, а не по одной характеристике.

Вывод: оптимальная платформа — та, что обеспечивает заданную нагрузку, совместимость, надёжность и разумные затраты на всём жизненном цикле.

## Вопрос 2. Регрессионное тестирование, локализация дефекта и оформление карточки ошибки

Регрессионное тестирование проверяет, что изменения в коде, конфигурации или зависимостях не нарушили ранее работающие функции. Его проводят после исправления ошибок, рефакторинга и выпуска новых возможностей. В набор включают самые важные пользовательские сценарии, тесты затронутых модулей и специальные проверки ранее найденных дефектов.

Локализация дефекта — поиск участка и условий, вызывающих ошибку. Сначала проблему воспроизводят на известной версии, собирают входные данные, логи и шаги; затем сужают область поиском по модулям, диагностическим сообщениям, сравнениям изменений Git и по необходимости git bisect. Важно разделять симптом и первопричину: «на странице пустая таблица» — симптом, «неверный фильтр SQL» — возможная причина, которую надо подтвердить.

Карточка ошибки (bug report) обычно содержит ID, краткое название, версию и окружение, предусловия, точные шаги воспроизведения, фактический и ожидаемый результат, серьёзность и приоритет, вложения и логи, ответственного и статус. Хороший пример: «При пустом артикуле кнопка сохранения создаёт заказ с пустым ID» вместо «Заказы сломаны». После исправления дефект перепроверяют и запускают регрессионные тесты.

Регрессионное тестирование проверяет, что после изменения не сломались функции, работавшие ранее. Его выполняют после исправлений, обновлений и объединения веток; набор важных проверок удобно автоматизировать. Если новый дефект обнаружен, сначала воспроизводят проблему, фиксируют входные данные и точные шаги, затем сравнивают поведение разных версий и по возможности локализуют изменение, вызвавшее ошибку. Карточка дефекта должна содержать название, окружение, шаги, ожидаемый и фактический результат, серьёзность, доказательства и версию программы. Чем точнее эти данные, тем проще разработчику исправить проблему и тестировщику проверить результат.

Вывод: регрессия предотвращает повторное появление ошибок, локализация находит причину, а грамотный баг-репорт делает исправление воспроизводимым.

## Практическое задание. Открытие и закрытие списка заказов

Условие (по скану преподавателя). Заказы Z1 — Новый — Север, Z2 — Готов — Центр, Z3 — Выдан — Юг. Пользователь — менеджер. Главное меню: 1 — «Заказы», 0 — «Выход». При 1 вывести все заказы и предложить команду «Назад» для возвращения к главному меню; 0 завершает программу. Неверная команда — ошибка. Заказы не изменяются.

### Решение на Python 3

[Открыть код](practice.py). Запуск из корня проекта

```sh
python docs/30/practice.py
```

### Как объяснить код преподавателю

Внешний while повторяет главное меню. При выборе 1 печатаем список и ждём слова «Назад» или команды 0. «Назад» возвращает в главное меню; 0 завершает всё приложение.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.

### Проверь себя

Ввод: 1 ↵ Назад ↵ 0   →   Ожидается: Список, повторное меню, завершение

Ввод: 5 ↵ 0   →   Ожидается: Ошибка, затем завершение
