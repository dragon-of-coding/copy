## Вопрос 1. Этапы внедрения PLM и оценка результатов внедрения

Внедрение PLM — организационно-технический проект по изменению процессов и способов работы с данными об изделии. Он начинается с анализа текущих процессов (as-is): где хранятся чертежи и спецификации, как согласуют изменения, какие проблемы возникают. Затем описывают целевую модель (to-be), требования, роли, границы проекта и измеримые показатели результата.

Далее выбирают платформу, проектируют модель данных, справочники, права и маршруты, планируют интеграцию с CAD/ERP и очистку данных. Проводят пилот на ограниченном участке, проверяют миграцию, обучают пользователей и собирают обратную связь. После устранения проблем систему постепенно тиражируют, организуют поддержку и совершенствование процессов. Критично обеспечить участие инженеров и руководства: установка ПО без изменения практик согласования не даст ожидаемого эффекта.

Оценка результатов включает сроки поиска документации, число ошибок из-за неверных ревизий, длительность согласований, полноту связей BOM, долю пользователей, реально работающих в системе, скорость инженерного изменения и затраты на сопровождение. Сравнивают значения «до/после» с учётом периода наблюдения и объёма операций.

Внедрение PLM начинают не с покупки лицензий, а с изучения текущих процессов и данных предприятия. Затем формируют цели, выбирают ключевые сценарии, настраивают роли и модель изделий, переносят справочники и документы, обучают пользователей. Полезен пилотный проект на одном изделии или подразделении: он выявляет проблемы до масштабного запуска. Эффект оценивают по измеримым показателям, например времени поиска нужного чертежа, числу ошибок в версиях документов, продолжительности согласования изменений и затратам на повторные операции. Успешное внедрение требует изменения рабочих привычек, а не только установки новой информационной системы.

Вывод: успех PLM — не факт установки сервера, а улучшение управляемости данных и инженерных процессов.

## Вопрос 2. Ручное развёртывание артефакта в тестовую среду GitLab и дымовая проверка приложения

Ручное развёртывание используют, когда установку требуется подтвердить после тестирования, например перед передачей сборки на стенд. В GitLab CI для job стадии deploy можно указать when: manual, environment: name: staging и команды, которые получают подготовленный артефакт, останавливают или обновляют сервис и запускают новую версию.

Задание должно работать с тем же проверенным артефактом, который сформирован на стадии package, а не непредсказуемо пересобирать исходники. Перед запуском проверяют права, доступность стенда, конфигурацию, секреты и наличие резервных копий при работе с данными. После развёртывания выполняют curl к /health, проверку входа и одного ключевого сценария.

Если smoke-тест не прошёл, задание отмечают неуспешным, сохраняют диагностические логи, принимают решение об исправлении или откате. Важно записать номер CI pipeline, коммит, версию, время, исполнителя и результат. Для защиты стенда настраивают правила запуска и ограничения окружения.

Ручное развёртывание в тестовую среду GitLab обычно означает, что сборка и проверка выполняются в CI, а job установки запускается человеком после разрешения. В задании используют условие when: manual и задают окружение environment, в котором будет выполняться команда. После передачи артефакта проверяют версию и базовые функции приложения, фиксируют результат в журнале. Такой подход полезен, когда перед развёртыванием нужно согласование или свободное окно работ. Ручной запуск не должен обходить тесты: задача установки должна зависеть от успешной сборки. При серьёзном сбое действуют по плану отката.

Вывод: ручной запуск — контрольный шлюз перед изменением среды, а автоматическая дымовая проверка подтверждает, что приложение после установки действительно работает.

## Практическое задание. Возврат пользователя к экрану входа

Условие (по скану преподавателя). Три учётные записи anna/111, ivan/222, olga/333. При успешном входе показать «Личный кабинет» и меню: 1 — выйти из учётной записи и вновь запросить логин/пароль; 0 — завершить программу. При неправильном входе повторить экран входа. Не путать выход из аккаунта и завершение программы.

### Решение на Python 3

[Открыть код](practice.py). Запуск из корня проекта

```sh
python docs/28/practice.py
```

### Как объяснить код преподавателю

Внешний while показывает экран входа, внутренний while — меню после удачного входа. Команда 1 завершает только внутренний цикл, команда 0 устанавливает обе управляющие переменные в False.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.

### Проверь себя

Ввод: anna ↵ 111 ↵ 1 ↵ olga ↵ 333 ↵ 0   →   Ожидается: Два входа и завершение работы
