## Вопрос 1. Форматы программных пакетов и назначение менеджеров пакетов

Пакет ПО — единица доставки и установки, включающая программу, метаданные, версию и сведения о зависимостях. Форматы различаются по платформе: .deb для Debian/Ubuntu, .rpm для ряда RPM-дистрибутивов, .msi для Windows Installer, .whl для Python, .jar для Java. Архив .zip сам по себе не всегда является установочным пакетом: в нём может не быть правил регистрации, зависимостей и удаления.

Менеджер пакетов автоматизирует поиск, загрузку, проверку, установку, обновление и удаление ПО. Примеры: APT и DNF для ОС, pip и uv для Python, npm для JavaScript. Менеджер использует репозитории и сведения о версиях, разрешает зависимости, а при наличии механизмов подписи проверяет происхождение пакетов.

Важные свойства пакета: идентификатор и версия, поддерживаемые архитектуры, зависимости, лицензия, контрольные суммы, сценарии установки и удаления. Для воспроизводимой сборки фиксируют версии зависимостей с помощью lock-файла, а не полагаются на неопределённое «самое новое». При обновлении проверяют совместимость; при удалении учитывают, нужно ли сохранять пользовательские данные и конфигурацию.

Пакет содержит программу, метаданные и сведения о зависимостях, а менеджер пакетов устанавливает, обновляет и удаляет такие компоненты по установленным правилам. Примеры: APT работает с пакетами Debian/Ubuntu, pacman — в Arch Linux, pip — с библиотеками Python. Формат пакета зависит от экосистемы: .deb, .rpm, Python wheel и другие. Менеджер учитывает версии и зависимости, а при установке из доверенного репозитория может проверять подписи. При этом версии пакетов и уровень совместимости важнее самого расширения файла: программа может установиться, но не запуститься из-за несовместимого API или системной библиотеки. Для повторяемого развёртывания фиксируют версии и источник зависимостей.

Пример: pip install package==1.2.3 задаёт конкретную версию Python-пакета; apt install nginx устанавливает сервер и необходимые системные зависимости из настроенных репозиториев. Вывод: пакет описывает поставляемую программу, менеджер обеспечивает её управляемый жизненный цикл.

## Вопрос 2. Разделение кода, конфигурации, секретов, данных и журналов при развёртывании

При развёртывании важно отделять то, что поставляется в версии, от того, что зависит от среды и возникает во время работы. Код и зависимости входят в пакет/образ; конфигурация задаёт адреса сервисов, порты и режимы; секреты содержат пароли, токены и ключи; данные — это изменяемая информация приложения; журналы — диагностические записи.

Код хранят в системе версий и пересобирают при изменении. Конфигурацию передают через переменные окружения и отдельные файлы, применяя проверку значений. Секреты размещают в специализированном хранилище или механизме secrets, ограничивают доступ и не печатают в логах. Данные хранят на постоянных томах, в БД или внешнем хранилище; их регулярно резервируют. Логи отправляют в стандартные потоки контейнера либо централизованную систему, задают ротацию и срок хранения.

Такое разделение позволяет обновить образ без потери данных, настроить разные среды одним и тем же артефактом и отозвать компрометированный ключ. Типовая ошибка — хранить БД внутри эфемерной файловой системы контейнера или включить .env с паролем в Git.

Код приложения, конфигурация, секреты, пользовательские данные и журналы выполняют разные задачи, поэтому хранить их в одной папке или контейнерном слое рискованно. Код и стандартные зависимости можно упаковать в образ, настройки окружения передавать отдельно, пароли хранить в защищённом источнике, постоянные данные — в томе или базе, а логи — выводить в систему сбора журналов. Так одну версию программы можно переносить из тестовой среды в рабочую. Например, подключение к учебной базе и к рабочей базе отличается настройкой DATABASE_URL, а не изменением исходного файла. Перед публикацией нужно убедиться, что в репозиторий и журналы не попали пароли или токены.

Вывод: среда остаётся управляемой, когда код неизменяем, настройки явны, секреты защищены, данные постоянны, а логи доступны для диагностики.

## Практическое задание. Фильтрация товаров по поставщику

Условие (по скану преподавателя). A1 — кеды — Альфа, A2 — ботинки — Бета, A3 — сандалии — Альфа. Ввести поставщика, отобрать совпадения без учёта регистра. «Все поставщики» отменяет фильтр. Если совпадений нет — «Товары не найдены».

### Решение на Python 3

[Открыть код](practice.py). Запуск из корня проекта

```sh
python docs/14/practice.py
```

### Как объяснить код преподавателю

При значении «Все поставщики» условие верно для каждой записи. Иначе сравниваем поставщика с введённым текстом после lower(). found позволяет отличить пустой результат от успешной фильтрации.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.

### Проверь себя

Ввод: альфа   →   Ожидается: A1 и A3

Ввод: Все поставщики   →   Ожидается: Все три товара
