## Вопрос 1. Жизненный цикл изделия и назначение PLM. Соотношение PDM и PLM

Жизненный цикл изделия охватывает замысел, проектирование, разработку, изготовление, поставку, эксплуатацию, модернизацию и утилизацию. На каждом этапе появляются данные: требования, чертежи, спецификации, модели, изменения, инструкции, результаты испытаний. Потеря связи между этими данными повышает число ошибок и затраты.

PLM (Product Lifecycle Management) — подход и совокупность информационных средств для управления сведениями об изделии и связанными процессами на всём жизненном цикле. PLM помогает координировать конструкторов, технологов, производство, снабжение, сервис, контролировать версии, согласования и изменения. Это не только программный продукт, а ещё роли, процессы и правила работы с инженерными данными.

PDM (Product Data Management) ориентирован прежде всего на управление данными о продукте: файлами CAD, метаданными, структурами изделия, версиями, правами доступа, связями и маршрутами согласования. PDM часто является важной составной частью PLM. Разница: PDM отвечает на вопрос «какие данные об изделии актуальны и как они связаны», а PLM — «как управлять изделием и процессами от идеи до завершения эксплуатации».

Для жизненного цикла физического изделия характерны связи между объектами: сборка состоит из деталей; каждая деталь имеет документацию, версию, исполнителя и состояние согласования. PDM хранит эти инженерные данные, отслеживает их актуальность и запрещает случайное использование устаревшего чертежа. PLM связывает данные с производственными и управленческими процессами: изменённая деталь может потребовать новой спецификации, закупки и инструкции по ремонту. PLM особенно полезен, когда над изделием работают разные подразделения. Простой пример: после изменения размера отверстия необходимо проверить чертёж, технологический маршрут, наличие нового инструмента и взаимозаменяемость запасных частей.

Пример: PDM хранит чертёж детали и спецификацию сборки; PLM дополнительно связывает изменение конструкции с закупками, производством, тестированием и сервисной документацией. Вывод: понятия пересекаются, но масштаб PLM шире.

## Вопрос 2. Структура .gitlab-ci.yml. Стадии validate, test и package в конвейере GitLab

.gitlab-ci.yml — YAML-файл в репозитории, описывающий автоматизированный конвейер GitLab CI/CD. В нём задают stages (порядок этапов), jobs (задания), команды script, образы image, переменные variables, правила rules, артефакты artifacts и условия выполнения. GitLab Runner выполняет задания в назначенной среде.

Validate — быстрые проверки структуры проекта: присутствие нужных файлов, корректность YAML/JSON, форматирование, линтеры, проверка компиляции. Test — модульные и интеграционные тесты, которые должны завершаться ненулевым кодом при дефекте. Package — сборка поставляемого артефакта: архива, wheel, JAR или Docker-образа. Как правило, упаковка должна происходить только после успешных проверок.

Пример минимальной структуры: stages: [validate, test, package], затем отдельные задания с stage: validate, stage: test, stage: package и соответствующими script. По умолчанию следующий этап ждёт успешного выполнения предыдущего; needs может менять граф зависимостей. В artifacts: paths: перечисляют результаты, которые нужно сохранить или передать дальше; простая запись файла в файловую систему Runner не гарантирует его сохранение.

Файл .gitlab-ci.yml описывает задания, но сами команды исполняет Runner. Этап validate отвечает за быстрый отказ при очевидных ошибках, test подтверждает поведение кода, package создаёт результат для передачи дальше. У каждого задания есть имя, stage и script; job считается неуспешным, если команда завершилась с ненулевым кодом. Успешный конвейер означает, что предусмотренные проверки пройдены, а не что программа гарантированно не содержит ошибок. Артефакты сохраняются отдельно от временного рабочего каталога Runner; их срок хранения можно ограничивать. Секретные токены лучше задавать в настройках CI/CD, а не записывать в репозитории.

Типичная ошибка: публиковать пакет до запуска тестов или хранить токены в YAML. Вывод: конвейер автоматизирует проверяемый переход от исходников к выпуску.

## Практическое задание. Просмотр списка заказов по роли

Условие (по скану преподавателя). Заказы Z1 — Новый — Север, Z2 — Готов — Центр, Z3 — Выдан — Юг. Ввести только роль. Менеджеру и администратору показать все три поля всех заказов. Для клиента и неизвестной роли — «Просмотр заказов недоступен».

### Как объяснить код преподавателю

Условие if разрешает вывод только двум ролям. Цикл последовательно печатает три поля каждой записи; для клиента срабатывает else.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.
