## Вопрос 1. Информационные объекты, метаданные и структура изделия в PLM

Информационный объект PLM — управляемая единица данных об изделии: деталь, узел, документ, 3D-модель, спецификация, требование, заявка на изменение, маршрут согласования. У каждого объекта обычно есть идентификатор, тип, свойства, версия или ревизия, состояние жизненного цикла и связи с другими объектами.

Метаданные — «данные о данных»: обозначение детали, автор, дата изменения, материал, масса, ответственный, статус «В разработке/На согласовании/Утверждено». Они облегчают поиск, фильтрацию, отчётность и правила доступа. Один и тот же CAD-файл может иметь несколько ревизий; метаданные помогают не перепутать актуальную и архивную версии.

Структура изделия (BOM, Bill of Materials) — иерархия «изделие → сборки → детали» с указанием количества и связей. Структура может различаться для конструкторских, производственных и сервисных задач: инженерная BOM показывает замысел конструктора, производственная — способ изготовления и комплектации. PLM хранит связи между элементами и обеспечивает управление изменениями: если заменилась деталь, можно выяснить, какие сборки затронуты.

Информационный объект PLM может представлять деталь, сборку, чертёж, документ или изменение. У объекта есть данные и метаданные: уникальный номер, название, автор, версия, статус, дата изменения и права доступа. Структура изделия (BOM) показывает, какие компоненты входят в сборку и в каком количестве. Связи важны не меньше самих файлов: по структуре можно найти, где используется конкретная деталь. Различают редакцию документа и состояние согласования: новый файл ещё не обязательно разрешён к производству. Поэтому PLM хранит историю версий и правила утверждения, чтобы сотрудники пользовались одной согласованной информацией.

Пример: объект «Ноутбук» связан с «Материнская плата», «Корпус», «Батарея»; у каждой детали собственные документы и версии. Вывод: PLM управляет не россыпью файлов, а связанными объектами и их жизненными состояниями.

## Вопрос 2. Автоматический запуск модульных тестов в GitLab CI и блокировка конвейера при дефекте

Модульные тесты проверяют небольшие единицы программы — функции, методы, классы — в контролируемых условиях. В GitLab CI их запускают заданием стадии test: Runner устанавливает среду, выполняет команду тестов и анализирует код завершения процесса. Для Python это может быть python -m unittest discover -s tests -v или pytest при установленной зависимости.

Если тестовый процесс возвращает нулевой код, задание считается успешным; при ненулевом — неуспешным, и следующие зависимые этапы по умолчанию не запускаются. Поэтому не следует добавлять || true или allow_failure: true к обязательным проверкам: это скрывает дефекты. Результаты удобно публиковать как artifacts:reports:junit и при необходимости отчёты покрытия.

Для надёжности тесты должны быть детерминированными, независимыми от порядка, иметь фиксированные тестовые данные и контролируемые внешние зависимости. Отдельно проверяют, что негативный тест действительно приводит к красному конвейеру. При выявленном дефекте разработчик воспроизводит его локально, исправляет код и подтверждает, что весь набор снова зелёный.

Автоматический тест в CI запускается после изменения кода, не требуя ручного открытия проекта. Для Python обычно устанавливают зависимости и выполняют python -m unittest или pytest, если он предусмотрен. Когда хотя бы один тест падает, команда возвращает ненулевой код, job становится неуспешным, а последующие зависимые этапы по обычной схеме не запускаются. Это и есть блокировка конвейера при дефекте. Важно проверять не только «зелёный статус», но и то, что тесты действительно обнаружены; ошибочная конфигурация может завершиться без проверки нужного кода. Вывод тестов и отчёт покрытия помогают разобраться в причине ошибки.

Вывод: тестирование в CI превращает проверку качества из ручной просьбы в обязательный автоматический барьер перед упаковкой и поставкой.

## Практическое задание. Сортировка товаров по возрастанию остатка

Условие (по скану преподавателя). Товары A1 — кеды — остаток 8, A2 — ботинки — 2, A3 — сандалии — 5. Отсортировать сами записи по остатку по возрастанию, напечатать артикулы, названия и остатки; затем назвать товар с минимальным остатком. Ввод не нужен.

### Решение на Python 3

[Открыть код](practice.py). Запуск из корня проекта

```sh
python docs/08/practice.py
```

### Как объяснить код преподавателю

Два вложенных цикла сравнивают соседние записи. Если у левого товара остаток больше, записи меняются местами через temp. Это простая сортировка обменом; вместе с товаром перемещаются все его поля.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.
