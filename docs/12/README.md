## Вопрос 1. Планирование версий и релизов программного продукта

Версия — идентификатор состояния продукта, релиз — подготовленный и предоставленный пользователям или другой среде выпуск конкретной версии. Версии позволяют различать функциональность и исправления; релиз дополнительно включает результаты тестирования, документацию, пакет поставки и решение о публикации.

Планирование релиза начинается с определения объёма (scope): какие требования, исправления и улучшения войдут в выпуск. Затем оценивают трудоёмкость, зависимости и риски, назначают ответственных, определяют дату стабилизации и критерии готовности. Учитывают совместимость, миграции данных, обратимость изменений, обязательные тесты и окно развёртывания. Для обозначения версий может использоваться SemVer: MAJOR — несовместимые изменения API, MINOR — обратно совместимая функциональность, PATCH — обратно совместимые исправления.

Релизный план содержит состав выпуска, контрольные точки, среду проверки, ограничения, порядок установки, проверку работоспособности и откат. Release notes объясняют пользователям, что изменилось. В Git состояние релиза отмечают тегом; при автоматической сборке тег помогает связать опубликованный пакет с исходным коммитом.

Версия показывает, какое состояние продукта поставлено пользователю, а релиз — организованную передачу этой версии. План релиза содержит состав изменений, ограничения, даты, ответственных, проверки, порядок установки и способ возврата к предыдущей версии. Полезно разделять исправления ошибок, новые функции и изменения, несовместимые со старым поведением. Например, при семантическом версионировании обозначение MAJOR.MINOR.PATCH соответствует несовместимым изменениям, новым совместимым функциям и исправлениям. Но использовать именно эту схему необязательно: важнее, чтобы правила были едины для команды. Перед выпуском готовят краткое описание изменений и подтверждение прохождения тестов.

Пример: в 1.4.0 добавили фильтр заказов, в 1.4.1 исправили ошибку отображения, а в 2.0.0 изменили формат внешнего API без полной обратной совместимости. Вывод: управлять релизом — значит гарантировать известный состав, качество и воспроизводимость поставки.

## Вопрос 2. Сборка, маркировка и запуск контейнерного образа. Сопоставление портов

Образ Docker — неизменяемый шаблон с приложением, библиотеками и метаданными; контейнер — запущенный экземпляр образа. Сборка выполняется docker build -t app:1.0 ., где -t задаёт имя и тег, а . — контекст. Тег удобен для чтения, но может быть переназначен; digest идентифицирует конкретное содержимое образа.

Запуск: docker run --rm --name app -p 8080:8000 app:1.0. В записи -p ХОСТ:КОНТЕЙНЕР порт 8080 доступен на машине-хосте, а 8000 — порт, на котором приложение должно слушать внутри контейнера. Директива EXPOSE 8000 документирует предполагаемый порт, но сама его не публикует. Если сервис внутри слушает только 127.0.0.1, публикация может не дать доступ снаружи контейнера: часто требуется слушать 0.0.0.0.

Проверяют результат через docker ps, docker logs app и запрос curl http://localhost:8080/health. Для передачи переменных используют -e, для данных — -v/--mount. При публикации в реестр выполняют docker tag app:1.0 registry.example/app:1.0, затем docker push после входа и проверки прав.

Команда docker build создаёт образ из Dockerfile, а docker run запускает контейнер на его основе. Тег образа, например app:1.2, помогает отличать версии, хотя тег сам по себе может быть переназначен, поэтому для точной идентификации используют digest. Опция -p 8080:8000 означает: порт 8080 на компьютере связан с портом 8000 внутри контейнера. Приложение должно слушать внутренний порт и нужный сетевой интерфейс, иначе проброс не поможет. Команды docker ps и docker logs полезны при проверке запуска. Публикация порта даёт доступ к сервису, поэтому нельзя без необходимости открывать наружу административные интерфейсы и базы данных.

Вывод: сборка создаёт образ, маркировка обозначает версию, запуск создаёт контейнер, а сопоставление портов связывает сеть хоста с сетью контейнера.

## Практическое задание. Разграничение прав при добавлении заказа

Условие (по скану преподавателя). Заказы Z1 — Новый, Z2 — Готов, Z3 — Выдан. Ввести роль и новый артикул; добавление доступно только администратору. Артикул должен быть непустым и уникальным. Иначе — «Добавление запрещено» для неадминистратора или ошибка для недопустимого артикула; список не менять.

### Решение на Python 3

[Открыть код](practice.py). Запуск из корня проекта

```sh
python docs/12/practice.py
```

### Как объяснить код преподавателю

Первое условие защищает операцию по роли. Затем проверяются пустота и повтор артикула. Лишь ветка else изменяет список, поэтому неверный запрос ничего не добавит.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.

### Проверь себя

Ввод: администратор ↵ Z4   →   Ожидается: Добавлен новый заказ

Ввод: менеджер ↵ Z4   →   Ожидается: Добавление запрещено
