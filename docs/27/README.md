## Вопрос 1. Документы сопровождения и развёртывания. Метрики и контроль качества

Документация развёртывания описывает, как установить, настроить, проверить и при необходимости откатить версию: требования к среде, состав поставки, порядок установки, конфигурацию, миграции, проверку и восстановление. Документы сопровождения позволяют эксплуатировать систему: паспорт, инструкции администратора и пользователя, схемы архитектуры, runbook, журнал инцидентов, регламент резервного копирования, база известных ошибок и история релизов.

Хорошая документация актуальна именно для установленной версии, содержит конкретные команды и ожидаемые результаты, указывает ответственных и не публикует пароли. Она должна позволять другому специалисту повторить операцию. Качество проверяют по понятности, полноте, воспроизводимости и соответствию фактической системе.

Метрики сопровождения: доступность (доля времени работы), частота инцидентов, MTTR (среднее время восстановления), повторяемость дефектов, скорость реакции. Для выпуска оценивают процент успешных развёртываний, долю изменений, вызвавших сбой, время восстановления, результаты smoke-тестов и число дефектов после релиза. Метрики интерпретируют с учётом нагрузки и критичности системы: одна величина сама по себе не характеризует качество.

Для сопровождения нужны документы, которые позволяют запускать и восстанавливать систему без помощи её первоначального разработчика: паспорт, инструкция установки, схема архитектуры, описание конфигурации, журнал изменений, план резервного копирования, порядок обработки инцидентов и контакты ответственных. Качество контролируют измеримыми показателями: время простоя, время восстановления, частота повторных ошибок, доля успешных развёртываний, число критичных дефектов. Метрика без цели мало полезна: нужно понимать, какое поведение считается нормальным и когда требуется вмешательство. Например, увеличение времени отклика после релиза служит сигналом для проверки, даже если программа формально запускается.

Вывод: документы сохраняют знания, а метрики помогают объективно выявлять проблемы и улучшать процесс.

## Вопрос 2. Воспроизводимый запуск приложения средствами Docker Compose

Docker Compose позволяет описать многоконтейнерное приложение в одном файле compose.yaml: сервисы, образы или правила сборки, сети, тома, переменные, порты и проверки состояния. Это особенно удобно, когда приложению требуется БД, очередь или кэш. Команда docker compose up -d --build создаёт или обновляет сервисы и запускает их в фоновом режиме.

Воспроизводимость требует фиксировать версии образов, зависимости, конфигурационные шаблоны и структуру томов. Например, сервис web использует образ приложения, а db — конкретную версию PostgreSQL с именованным томом; оба подключены к общей сети Compose и обращаются друг к другу по имени сервиса. Переменные задают через environment, env_file или secrets, но чувствительные данные не включают в репозиторий.

Для контроля применяют docker compose config (проверка собранной конфигурации), docker compose ps, docker compose logs, docker compose exec. depends_on определяет порядок зависимостей; с condition: service_healthy может дождаться успешной проверки healthcheck, но не заменяет повторные попытки подключения в коде приложения. Останавливают сервисы через docker compose down, осторожно с -v, которое может удалить тома.

Docker Compose описывает несколько связанных контейнеров и их настройки в одном YAML-файле: services, image или build, ports, environment, volumes, networks. Команда docker compose up -d запускает сервисы, а docker compose down останавливает и удаляет созданные контейнеры и сети; постоянные именованные тома обычно сохраняются без дополнительного флага удаления. Compose удобен для повторяемости: не нужно вручную вводить длинные docker run команды для каждого сервиса. Важно закреплять нужные версии образов, отделять секреты от репозитория и помнить, что depends_on без дополнительных условий не гарантирует готовность зависимого приложения принимать запросы.

Вывод: Compose превращает ручную настройку нескольких контейнеров в документированное и повторяемое описание приложения.

## Практическое задание. Проверка прав при удалении заказа

Условие (по скану преподавателя). Заказы Z1 — Новый, Z2 — Готов, Z3 — Выдан. По введённой роли и артикулу разрешить удаление лишь администратору; для остальных ролей — «Удаление заказов запрещено». Для администратора с неизвестным артикулом — «Заказ не найден»; при успехе вывести новый список.

### Решение на Python 3

[Открыть код](practice.py). Запуск из корня проекта

```sh
python docs/27/practice.py
```

### Как объяснить код преподавателю

Роль проверяется до поиска артикула: постороннему пользователю сразу отказывают. Если роль правильная, проверяют наличие заказа и лишь затем применяют del.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.

### Проверь себя

Ввод: администратор ↵ Z3   →   Ожидается: Остались Z1 и Z2

Ввод: менеджер ↵ Z3   →   Ожидается: Удаление заказов запрещено
