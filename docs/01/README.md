## Вопрос 1. Назначение и область применения ГОСТ Р ИСО/МЭК 12207-2010. Адаптация стандарта к проекту

ГОСТ Р ИСО/МЭК 12207-2010 — национальный стандарт «Информационная технология. Системная и программная инженерия. Процессы жизненного цикла программных средств». Он устанавливает общую структуру процессов, которыми управляют на протяжении существования программного продукта: от возникновения потребности и приобретения или разработки до эксплуатации, сопровождения и прекращения использования. Стандарт нужен, чтобы заказчик, разработчик, поставщик и сопровождающая организация одинаково понимали обязанности, действия, результаты и контрольные точки.

В стандарте рассматриваются процессы соглашения (приобретение и поставка), организационного обеспечения проекта (управление ресурсами, качеством, инфраструктурой), процессы управления проектом, технические процессы разработки и применения программных средств, а также процессы поддержки. Для каждого процесса описываются его назначение и ожидаемые результаты. Важный принцип: стандарт не требует единственной модели жизненного цикла. Его можно применять в последовательной, итерационной и гибкой разработке.

Адаптация (tailoring) — осознанный выбор и настройка процессов, действий, ролей и документов для конкретного проекта. Например, небольшому учебному веб-приложению не нужен тяжёлый многоступенчатый регламент закупок, но нужны управление требованиями, версиями, тестирование, развёртывание и исправление дефектов. При адаптации определяют размер и риски проекта, перечень применяемых процессов, распределение ответственности, необходимые артефакты и критерии приёмки; исключения документируют и обосновывают. Нельзя бездумно выкидывать проверки безопасности и качества, если они критичны для продукта.

Важно различать жизненный цикл и модель его организации. Жизненный цикл включает все состояния ПО, а модель (каскадная, итерационная, гибкая) задаёт порядок выполнения работ. Стандарт описывает не конкретную команду или инструмент, а процессы и ожидаемые результаты. Адаптация нужна, чтобы не создавать лишнюю бюрократию, но сохранить важные проверки. Например, в маленьком проекте один разработчик может одновременно отвечать за код и тестирование, однако результаты тестирования всё равно должны быть зафиксированы. При выборе процессов полезно составить таблицу: процесс, ответственный, результат, способ проверки. Так проверяющий увидит, что требования не просто объявлены, а действительно выполнены.

Пример: для сайта-каталога результатами могут быть техническое задание, репозиторий, тесты, инструкция установки, версия для развёртывания и акт приёмки. Вывод: ГОСТ определяет что нужно обеспечить и проверить, а команда выбирает как именно это сделать.

## Вопрос 2. Создание репозитория Git, настройка автора и формирование первого контролируемого состояния

Git — распределённая система контроля версий: она фиксирует снимки состояния файлов, авторов изменений и историю, позволяет возвращаться к предыдущим версиям и совместно разрабатывать проект. Репозиторий — каталог с рабочими файлами и скрытой служебной папкой .git, в которой хранятся объекты и история.

Для нового проекта выполняют git init, затем задают автора через git config user.name "Имя" и git config user.email "почта@example.com" (без --global — только для текущего репозитория; с --global — для всех репозиториев пользователя). Командой git status смотрят изменения, git add . помещают нужные файлы в индекс (staging area), а git commit -m "Initial commit" создают первый коммит. Важно понимать три состояния: рабочая директория, индекс и сохранённый коммит.

Перед первым коммитом создают .gitignore для временных файлов, кэша, виртуальных окружений, паролей и локальных конфигураций. Git не создаёт коммиты автоматически и не отправляет их на сервер. Для публикации добавляют удалённый адрес (git remote add origin URL) и отправляют ветку (git push -u origin main), предварительно убедившись в её названии.

Первое контролируемое состояние — это не просто папка с программой, а зафиксированный набор файлов, к которому можно вернуться. Сначала создаём проект, запускаем git init и смотрим git status; затем решаем, какие файлы нужно отслеживать. git add README.md добавляет конкретный файл в индекс, git add . — изменения во всём текущем каталоге; поэтому второй вариант требует предварительной проверки. git commit сохраняет состояние в локальной истории. Команда git diff показывает неиндексированные изменения, а git diff --cached — изменения, готовые к коммиту. Автор, указанный в git config, записывается в новые коммиты; изменение настройки не переписывает старые. Для первого коммита полезно проверить, что пароль, .venv и __pycache__ не попали в репозиторий.

Проверка результата: git log --oneline показывает первый коммит, git status сообщает о чистом рабочем каталоге. Вывод: первый коммит — воспроизводимая контрольная точка проекта.

## Практическое задание. Авторизация пользователя

Условие (по скану преподавателя). Три аккаунта: anna/111 — клиент, ivan/222 — менеджер, olga/333 — администратор. За одну попытку проверить логин и пароль с учётом регистра. При совпадении вывести «Вход выполнен» и роль, иначе — «Неверный логин или пароль».

### Как объяснить код преподавателю

Словарь users хранит для каждого логина пароль и роль. Оператор in проверяет наличие логина, а сравнение == — правильность пароля; две проверки не позволяют войти по одному совпадению.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.
