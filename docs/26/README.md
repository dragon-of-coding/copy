## Вопрос 1. Технические процессы, реализация и поддержка программных средств в жизненном цикле

Технические процессы превращают потребности заинтересованных сторон в программный продукт и обеспечивают его работоспособность. Они охватывают анализ требований, архитектуру, проектирование, реализацию компонентов, интеграцию, верификацию, валидацию, переход в эксплуатацию, использование, сопровождение и вывод из эксплуатации. Конкретный набор и названия отдельных процессов зависят от редакции стандарта и принятой модели проекта.

Реализация — создание программных компонентов по требованиям и проектным решениям: написание кода, сборка, статические проверки и модульные тесты. Интеграция объединяет компоненты в систему; верификация устанавливает соответствие заданным требованиям и проектным спецификациям («сделали правильно?»), валидация подтверждает пригодность для нужд пользователя («сделали нужное?»).

Поддержка включает корректировку ошибок, адаптацию к изменениям платформы, обновление зависимостей, мониторинг, управление версиями и обращения пользователей. Цикл не заканчивается после первой поставки: эксплуатационные наблюдения формируют новые требования, изменения проходят проверки и выпускаются новой версией. Все работы связаны управлением конфигурацией и документированием.

Технические процессы охватывают определение потребностей и требований, проектирование, реализацию, интеграцию, проверку, внедрение, эксплуатацию и дальнейшую поддержку продукта. При реализации разработчик преобразует требования и проектные решения в работающий код, но результат должен сопровождаться тестами и документацией. Поддержка включает исправление дефектов, адаптацию к изменившимся условиям и контролируемое обновление версий. Между этапами существует обратная связь: ошибка, обнаруженная при проверке, может означать проблему требований, архитектуры или кода. Важно сохранять результаты каждого этапа, чтобы понимать происхождение решения и оценивать последствия следующих изменений.

Вывод: технические процессы обеспечивают непрерывную связь от требований через код и тесты к эксплуатации и последующим улучшениям.

## Вопрос 2. Безопасная отмена ошибочного коммита командой git revert и сохранение истории изменений

git revert не удаляет существующий коммит. Она создаёт новый коммит с обратными изменениями по отношению к выбранному. Это безопасный способ отмены в общей опубликованной ветке, потому что история не переписывается, а факт ошибки и её исправления остаётся прослеживаемым.

Порядок: git log --oneline — найти ошибочный коммит; git revert <hash> — сформировать обратный коммит; проверить код и тесты; git push — опубликовать результат. Если изменения конфликтуют с более поздними правками, Git остановится для ручного разрешения конфликтов. При успешном revert можно восстановить нужную функциональность отдельным новым коммитом.

Отличие от git reset: reset перемещает указатель ветки и может убрать коммиты из её истории; с --hard он также может уничтожить незакоммиченные изменения в рабочем каталоге. На общей ветке reset с принудительной публикацией создаёт проблемы коллегам. revert предпочтительнее именно для уже опубликованных изменений. Отмена merge-коммита может потребовать указать основного родителя -m, поэтому её проводят особенно внимательно.

git revert создаёт новый коммит, который отменяет изменения выбранного предыдущего коммита. История при этом не переписывается — это безопаснее для общей ветки, где коллеги могли уже получить ошибочное изменение. Сначала находят хеш через git log --oneline, затем выполняют git revert <хеш>, проверяют итоговый diff и запускают тесты. Если изменения затрагивают код, который позже был изменён, может возникнуть конфликт; его нужно разрешить, как при слиянии. В отличие от git reset --hard, revert не отбрасывает другие локальные коммиты и не переносит ветку назад. При этом отмена кода не всегда автоматически отменяет изменения базы данных, сделанные во время работы приложения.

Вывод: git revert исправляет ошибку новым контролируемым действием, не скрывая историю проекта.

## Практическое задание. Удаление товара с подтверждением

Условие (по скану преподавателя). Каталог A1 — кеды, A2 — ботинки, A3 — сандалии. Пользователь — администратор. Только если товар найден, спросить подтверждение «да/нет». При «да» удалить и вывести остаток каталога, при «нет» отменить, иначе сообщить ошибку. Неизвестный артикул — «Товар не найден».

### Решение на Python 3

[Открыть код](practice.py). Запуск из корня проекта

```sh
python docs/26/practice.py
```

### Как объяснить код преподавателю

Второй запрос появляется только для существующего товара. Удаление выполняется строго при ответе «да»; «нет» и неправильное значение оставляют каталог как был.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.

### Проверь себя

Ввод: A1 ↵ да   →   Ожидается: A1 удалён

Ввод: A1 ↵ нет   →   Ожидается: Удаление отменено
