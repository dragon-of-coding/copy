## Вопрос 1. Управление инженерными изменениями и согласование изменений в PLM

Инженерное изменение — управляемое изменение характеристик, состава, документации или технологии изготовления изделия. Причинами бывают дефект, новое требование заказчика, замена материала, снижение стоимости или совершенствование конструкции. Изменение одного элемента может затронуть связанные сборки, закупки, испытания, складские остатки и сервис.

Типовой цикл: 1) регистрация запроса на изменение (ECR), 2) описание причины и желаемого результата, 3) анализ влияния на BOM, документы, стоимость и сроки, 4) согласование ответственными специалистами, 5) выпуск распоряжения или извещения об изменении (ECO/ECN), 6) реализация, проверка и изменение ревизий, 7) закрытие и архивирование решения. Названия и детализация документов могут отличаться по организации.

PLM автоматизирует маршрут согласования, ведёт роли и статусы, фиксирует авторов решений, не позволяет несанкционированно редактировать утверждённые данные и сохраняет историю. Это особенно важно, когда одновременно работают конструктор, технолог и производство. Анализ влияния обязателен: нельзя просто заменить чертёж, не проверив, где используется деталь.

Инженерное изменение начинается с предложения или выявленного несоответствия. Затем оценивают затронутые детали, документы, стоимость, сроки, производство, безопасность и запасы. По результатам согласования изменение разрешают либо отклоняют, назначают исполнителей и выпускают обновлённые версии объектов. PLM помогает связать основание изменения, согласующих лиц, новые документы и конкретные изделия, на которые оно влияет. Например, замена материала корпуса требует не только изменить чертёж, но и проверить характеристики, поставщиков и испытания. История согласования позволяет объяснить, почему изделие стало именно таким, а не просто видеть последнюю версию файла.

Пример: новая версия крепежа требует изменения спецификации, инструкций сборки и закупок. Вывод: управление изменениями в PLM гарантирует согласованность всей технической информации.

## Вопрос 2. Правила запуска заданий GitLab CI для веток, тегов и запросов на слияние

GitLab CI может запускать разные задания в зависимости от типа события: push в ветку, создание тега, merge request, ручной запуск и расписание. Для управления служит rules, где используют предопределённые переменные: CI_COMMIT_BRANCH, CI_COMMIT_TAG, CI_PIPELINE_SOURCE и другие. Сам факт наличия файла .gitlab-ci.yml не означает, что каждое задание должно исполняться при любом событии.

Например, быстрые проверки запускают для веток и merge requests, сборку релиза — только при теге версии, а развёртывание в production — вручную и только из защищённой ветки/тега. Условия записывают в определённом порядке, потому что GitLab использует первое подходящее правило. when: manual означает запуск по подтверждению; when: never исключает задание при совпадении.

Для безопасности учитывают права Runner и доступ к секретам, разделяют тестовое и боевое окружение. Токен публикации не должен быть доступен непроверенным веткам. Не стоит одновременно без необходимости создавать несколько конвейеров на один push и merge request; правила верхнего уровня workflow: rules помогают контролировать возникновение самих конвейеров.

Не каждый коммит должен запускать абсолютно все работы. В GitLab правила rules позволяют выбирать, когда выполняется задание: при push в ветку, создании тега, запросе на слияние или изменении определённых файлов. Например, для каждого merge request можно запускать линтер и тесты, а сборку релизного пакета — только для тега версии. Правила проверяют по порядку, и неправильное условие способно случайно пропустить нужную проверку. Важно различать ветку и тег: ветка обычно перемещается с новыми коммитами, а тег используется для обозначения конкретной точки истории. Защищённые ветки и правила проверки препятствуют обходу обязательных тестов.

Вывод: правила запуска определяют, какую проверку и в каком контексте выполнять, а не только порядок стадий.

## Практическое задание. Изменение пункта выдачи заказа

Условие (по скану преподавателя). Заказы Z1 — Новый — Север, Z2 — Готов — Центр, Z3 — Выдан — Юг. Пользователь — администратор. Ввести артикул и новый непустой пункт выдачи. При успехе изменить только адрес и показать список. При ошибке оставить данные прежними.

### Решение на Python 3

[Открыть код](practice.py). Запуск из корня проекта

```sh
python docs/18/practice.py
```

### Как объяснить код преподавателю

Цикл находит нужный заказ. Присваивание order[2] = pickup выполняется только при непустом адресе; артикул и статус не затрагиваются. После цикла выбираем сообщение об успехе или ошибке.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.

### Проверь себя

Ввод: Z1 ↵ Запад   →   Ожидается: Адрес Z1 стал Запад

Ввод: Z1 ↵ пустая строка   →   Ожидается: Ошибка, список не изменён
