## Вопрос 1. Управление обращениями, проблемами и изменениями при сопровождении системы

При сопровождении важно различать обращение, инцидент, проблему и изменение. Обращение — запрос пользователя, например на помощь или доступ. Инцидент — незапланированное нарушение или ухудшение услуги. Проблема — установленная или предполагаемая первопричина одного или нескольких инцидентов. Изменение — контролируемое преобразование системы для исправления, улучшения или настройки.

Управление обращениями включает регистрацию, категорию, приоритет, назначение исполнителя, коммуникацию и закрытие с подтверждением результата. Управление инцидентами нацелено на быстрое восстановление работы, даже если временно используется обходное решение. Управление проблемами ищет корневую причину, применяет анализ логов и повторяемости. Управление изменениями оценивает влияние, риск, окно установки, проверку и план отката.

Пример: пользователи жалуются на ошибки печати (обращения); служба печати недоступна (инцидент); причиной оказалась утечка памяти в драйвере (проблема); обновление драйвера — изменение. Каждое действие фиксируется в системе заявок и связывается с остальными записями.

При сопровождении важно не смешивать три понятия. Обращение пользователя регистрирует запрос или сообщение о неисправности; инцидент фиксирует нарушение сервиса; проблема ищет его первопричину; запрос на изменение описывает предлагаемые действия и риски. Для каждого обращения указывают категорию, степень влияния, срочность, ответственного и состояние. Перед внедрением изменения оценивают влияние на пользователей, готовят тесты, резервную копию и откат. Если одинаковая ошибка возникает несколько раз, недостаточно каждый раз перезапускать сервис: нужно выяснить причину и устранить её. После изменения обновляют документы и контролируют, что новые ошибки не появились.

Основные показатели: среднее время реакции, время восстановления, доля повторных инцидентов, процент успешных изменений. Вывод: цель процессов — не просто закрывать заявки, а стабильно улучшать сервис.

## Вопрос 2. Создание безопасного Dockerfile и назначение файла .dockerignore

Dockerfile задаёт команды сборки образа: базовый FROM, рабочую директорию WORKDIR, копирование COPY, установку зависимостей RUN, команду запуска CMD/ENTRYPOINT. Безопасность начинается с проверенного минимального базового образа, поддерживаемой версии среды и минимального набора установленных пакетов.

Рекомендуется сначала копировать файл зависимостей, устанавливать их фиксированные версии, а затем копировать исходники: это улучшает воспроизводимость и кэширование слоёв. Приложение по возможности запускают от отдельного пользователя через USER, не выставляют лишние порты и не кладут внутрь токены или пароли. Для проверки наличия уязвимостей сканируют образ и регулярно обновляют зависимости; изменение базового тега может изменить состав образа, поэтому для строгой воспроизводимости используют digest.

.dockerignore исключает файлы из контекста сборки: .git, .venv, __pycache__, отчёты, большие локальные данные и .env. Это ускоряет передачу контекста и снижает риск случайного попадания конфиденциальных данных в образ. Однако .dockerignore не заменяет управление секретами: секреты лучше вообще не хранить рядом с исходниками.

Dockerfile превращается в образ в процессе сборки. Команды обычно выполняются по слоям; правильный порядок COPY и установки зависимостей позволяет использовать кэш сборки. Лучше выбирать официальный минимальный базовый образ с подходящей версией, не устанавливать ненужное ПО и не запускать приложение от root без необходимости. Файл .dockerignore нужен, чтобы папки .git, .venv, кэши и локальные секреты не отправлялись в контекст сборки. Он не заменяет .gitignore: первый влияет на Docker-сборку, второй — на отслеживание Git. Безопасность также требует обновления зависимостей и проверки образа на уязвимости.

Вывод: безопасная сборка = минимальный образ + управляемые зависимости + ограниченные права + отсутствие секретов в слоях + проверка итогового образа.

## Практическое задание. Выбор роли при авторизации

Условие (по скану преподавателя). Учётные записи client/111, manager/222, admin/333. После проверки логина и пароля показать роль и предусмотренные права просмотра или изменения. Если данные неправильные — «Доступ запрещён». Выполнять сами операции не нужно.

### Решение на Python 3

[Открыть код](practice.py). Запуск из корня проекта

```sh
python docs/07/practice.py
```

### Как объяснить код преподавателю

После проверки пароля переменная role определяет текст доступных действий. Код только выводит права, как требует условие, а не пытается создавать реальные меню или операции.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.

### Проверь себя

Ввод: manager ↵ 222   →   Ожидается: Роль и два действия просмотра

Ввод: admin ↵ 000   →   Ожидается: Доступ запрещён
