## Вопрос 1. Сетевая подсистема и средства удалённого управления компьютерной платформой

Сетевая подсистема обеспечивает обмен данными между узлами: сетевые адаптеры, драйверы, коммутаторы, маршрутизаторы, протоколы IP, TCP/UDP, DNS, фильтры и межсетевые экраны. При установке серверного ПО оценивают IP-адреса, маршрутизацию, DNS, доступность портов, пропускную способность, задержки и настройки безопасности.

Удалённое управление позволяет администратору конфигурировать и обслуживать систему без физического доступа. Для Linux часто используют SSH: шифрованный канал, проверка ключа сервера и аутентификация пользователя (предпочтительно ключами). Для Windows возможны RDP, PowerShell Remoting/WinRM и средства корпоративного управления. Для оборудования серверного класса существуют отдельные контроллеры out-of-band управления (например IPMI/iDRAC/iLO), работающие даже при неисправной ОС.

Безопасная практика: отдельные учётные записи, минимальные права, ограничение по сети и firewall, журналы входа, обновления, MFA там, где поддерживается, и запрет передачи паролей открытым текстом. Проверка подключения состоит из последовательных шагов: IP-связность, порт, служба, аутентификация, права пользователя.

Сетевая подсистема включает сетевую карту, драйвер, адресацию, маршрутизацию и службы, через которые компьютер обменивается данными. Для удалённого управления часто используют SSH в Linux и удалённый рабочий стол либо PowerShell Remoting в Windows. SSH обычно работает через TCP-порт 22, но номер можно настроить; главное — чтобы служба работала и соединение не блокировал межсетевой экран. Ключевая аутентификация позволяет не передавать пароль при каждом входе. При диагностике сначала проверяют сеть и адрес, затем доступность порта, состояние службы, права пользователя и журналы ошибок. Успешный ping ещё не доказывает, что SSH доступен.

Пример: ping успешен, но SSH не подключается: ICMP-ответ ещё не доказывает, что на TCP/22 есть слушающий сервер или разрешающий firewall. Вывод: удалённое управление требует как сетевой доступности, так и безопасной аутентификации.

## Вопрос 2. Модульное тестирование средствами unittest. Проверка исключений и общих данных тестов

unittest — модуль стандартной библиотеки Python для модульного тестирования. Тесты обычно оформляют как методы test_* класса, наследуемого от unittest.TestCase. С помощью self.assertEqual, self.assertTrue, self.assertIn проверяют ожидаемое поведение, а self.assertRaises удостоверяется, что ошибочный ввод вызывает нужное исключение.

Проверка исключения: with self.assertRaises(ValueError): parse_price("abc"). Тест считается успешным только если внутри блока произошло именно ожидаемое исключение. Для проверки текста ошибки можно использовать assertRaisesRegex. Это важно, потому что корректная реакция на некорректные данные — часть требований.

Общие тестовые данные подготавливают в setUp() перед каждым тестом и удаляют в tearDown() после него; для общеклассовых ресурсов существуют setUpClass() и tearDownClass(). При работе с временными файлами удобно использовать tempfile.TemporaryDirectory(), чтобы тесты не портили пользовательские документы и не зависели от предыдущих запусков. Тесты запускают командой python -m unittest discover -v.

В unittest тесты объединяют в классы, наследующиеся от unittest.TestCase. Методы с именем test_ запускаются автоматически; методы setUp и tearDown готовят окружение и убирают за ним после каждого теста. Проверки assertEqual, assertTrue и assertRaises сравнивают фактический результат с ожидаемым. Например, для функции деления полезно проверить обычное значение и исключение ZeroDivisionError при нуле. Тест не должен зависеть от результата другого теста: общий изменяемый список может сделать поведение непредсказуемым. Запуск python -m unittest discover позволяет найти тесты, а результат показывает количество выполненных проверок и ошибки.

Вывод: хорошие модульные тесты изолированы, проверяют и нормальное, и ошибочное поведение, а фикстуры гарантируют воспроизводимость.

## Практическое задание. Изменение статуса заказа

Условие (по скану преподавателя). Заказы Z1 — Новый, Z2 — Готов, Z3 — Выдан. Пользователь — администратор. По артикулу заменить статус только на один из допустимых: «Новый», «Готов», «Выдан». При неизвестном заказе или недопустимом статусе показать ошибку и не менять запись.

### Решение на Python 3

[Открыть код](practice.py). Запуск из корня проекта

```sh
python docs/15/practice.py
```

### Как объяснить код преподавателю

Сначала проверяем, есть ли артикул в словаре, затем проверяем допустимый статус. Только после этих двух проверок присваиваем orders[sku] новое значение.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.

### Проверь себя

Ввод: Z2 ↵ Выдан   →   Ожидается: Статус Z2 изменён

Ввод: Z2 ↵ Отмена   →   Ожидается: Недопустимый статус
