## Вопрос 1. Типовая последовательность установки программного обеспечения и контроль результата

Типовая процедура установки начинается с подготовки: уточняют требования, целевую платформу, дистрибутив, согласования и точку восстановления. Затем проверяют подлинность и целостность пакета, свободные ресурсы, права, сетевой доступ, зависимости и несовместимые версии. При необходимости останавливают связанные службы и делают резервную копию.

Далее проводят установку: распаковывают или запускают пакетный менеджер, создают каталоги, устанавливают зависимости, регистрируют службы, задают конфигурацию и выполняют миграции. Все шаги фиксируют в журнале. После установки выполняют контроль: процесс стартует, логи не содержат критических ошибок, основные функции работают, подключение к БД и сети есть, версия соответствует ожидаемой.

Ввод в эксплуатацию включает smoke-тест, приёмочные проверки, мониторинг, назначение ответственных и передачу документации. При неуспехе применяется заранее подготовленный откат: возврат предыдущего пакета/образа и восстановление совместимых данных. Сложные миграции БД требуют особого плана, потому что восстановление старого кода не всегда восстанавливает прежнюю схему.

Обычная установка включает подготовку, резервное копирование, получение проверенного дистрибутива, установку зависимостей, настройку, запуск и послепусковую проверку. На каждом этапе нужно знать ожидаемый результат. Например, после установки службы проверяют её состояние, порт и обращение к главной функции; после миграции базы — целостность ключевых данных. Установка не считается успешной лишь потому, что программа завершилась с кодом ноль: важно проверить реальную работу продукта. Для повторяемости ведут журнал с версией, временем, командами, проблемами и именем исполнителя. В случае неудачи возвращаются к заранее сохранённому состоянию, а не импровизируют с удалением файлов.

Вывод: установка считается завершённой только после подтверждённого работоспособного состояния, а не после сообщения установщика «успешно».

## Вопрос 2. Резервное копирование данных, процедура отката и состав инструкции runbook

Резервное копирование создаёт отдельную копию данных, позволяющую восстановить систему после сбоя или ошибочного действия. Используют полные, инкрементальные и дифференциальные копии; выбирают расписание и срок хранения. Важны RPO (допустимая потеря данных во времени) и RTO (допустимое время восстановления). Успешная операция создания бэкапа не доказывает его пригодность — нужно периодически выполнять тестовое восстановление.

Откат (rollback) — возврат к предыдущему работоспособному состоянию после неудачного изменения. Для него заранее фиксируют исходную версию, резервную копию, последовательность действий, критерии запуска отката, ответственных и проверки после восстановления. Иногда вместо отката старой миграции безопаснее сделать совместимую исправляющую миграцию.

Runbook — пошаговая эксплуатационная инструкция для штатных и аварийных действий. Обычно содержит назначение, условия начала, необходимые доступы и команды, порядок установки/перезапуска, ожидаемые результаты, проверку здоровья, действия при ошибке, откат, контакты и ссылки на логи. Команды должны быть проверены, а секреты не должны храниться в открытом тексте.

Резервная копия нужна для восстановления данных после ошибки, сбоя или повреждения; откат версии приложения решает другую задачу — возврат к прежнему рабочему коду. Если релиз изменил структуру базы, простой откат исполняемого файла может не сработать: нужна совместимая схема либо заранее подготовленный способ восстановления. Runbook — пошаговая эксплуатационная инструкция с командами, признаками успеха, ответами на ошибки, ответственными и контактами. Копии следует периодически проверять восстановлением, иначе их наличие не гарантирует полезность. Перед обновлением определяют, какой простой допустим, сколько данных можно потерять и как быстро требуется восстановить сервис.

Вывод: бэкап создаёт возможность восстановления, откат описывает возврат изменений, а runbook помогает исполнить процедуру быстро и одинаково.

## Практическое задание. Обозначение товаров с большой скидкой

Условие (по скану преподавателя). Товары: кеды — скидка 10%, ботинки — 20%, сандалии — 15%. Показать название и скидку каждого товара; только при скидке строго больше 15% дополнительно пометить «Повышенная скидка». В конце сообщить количество отмеченных товаров. Ввод не нужен.

### Решение на Python 3

[Открыть код](practice.py). Запуск из корня проекта

```sh
python docs/19/practice.py
```

### Как объяснить код преподавателю

Строгое сравнение > 15 не включает ровно 15%. Переменная count увеличивается на один только для помеченных записей; в конце это итоговое количество.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.
