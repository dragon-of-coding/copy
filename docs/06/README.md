## Вопрос 1. Процесс жизненного цикла программного средства: цель, результаты и подтверждающие свидетельства

Процесс жизненного цикла — организованная совокупность взаимосвязанных действий, преобразующих входные данные в выходные результаты на протяжении существования ПО. У процесса есть назначение (зачем нужен), участники, входы, действия, результаты и признаки успешного выполнения. Стандарт описывает процессы через цели и ожидаемые результаты, а компания выбирает конкретные инструменты и документы.

Например, процесс управления требованиями нужен для согласования и актуализации требований. Ожидаемые результаты: зарегистрированные требования, известные изменения, обеспеченная трассируемость и согласованные решения. Процесс тестирования нужен для выявления несоответствий; его результаты — отчёты об исполнении тестов, найденные дефекты и решение о готовности. Процесс развёртывания заканчивается проверенной установкой и передачей в эксплуатацию.

Подтверждающие свидетельства (objective evidence) — наблюдаемые и сохраняемые доказательства, что результат достигнут: протоколы испытаний, коммиты, записи CI, утверждённые требования, артефакты сборки, журналы релизов, акты приёмки. Свидетельства должны относиться к нужной версии и быть проверяемыми. Само утверждение «всё протестировано» без отчёта слабее, чем список тестов и их результаты.

У процесса жизненного цикла есть цель, входные данные, действия, выходные результаты и критерии завершения. Например, процесс верификации использует требования и созданный код, выполняет проверки и выдаёт протоколы тестирования. Подтверждающие свидетельства — это наблюдаемые доказательства выполнения работ: журналы сборки, протоколы, коммиты, подписанные документы или отчёты об ошибках. Нельзя считать процесс выполненным только потому, что разработчик сказал «всё работает». Нужно отличать проверку соответствия спецификации (верификацию) от подтверждения пригодности продукта для потребностей пользователя (валидации). Результат оценивают по критериям, которые заданы заранее.

Вывод: качество процесса оценивают не числом заполненных бумаг, а достигнутыми результатами и возможностью их объективно подтвердить.

## Вопрос 2. Атомарные коммиты в Git. Подготовка изменений и просмотр git diff

Коммит — сохранённая версия дерева файлов с метаданными автора, времени и сообщения. Атомарный коммит логически посвящён одному завершённому изменению: например, исправлению одной ошибки, добавлению одной функции или обновлению документации. Он не обязательно меняет один файл, но все его изменения должны решать одну связанную задачу.

Рабочий порядок: git status — проверить изменённые файлы; git diff — посмотреть ещё не добавленные в индекс изменения; git add <файл> или git add -p — выбрать нужные участки; git diff --cached — проверить то, что войдёт в коммит; git commit -m "Fix order status validation" — зафиксировать. Если проверки не прошли, коммит откладывают. Не следует включать случайные отладочные файлы, секреты или не относящиеся к задаче изменения.

Атомарность помогает при git revert, git bisect, код-ревью и анализе причин дефекта. Хорошее сообщение коммита объясняет, что изменено и при необходимости почему. Если изменения случайно оказались в индексе, git restore --staged <файл> снимет их из индекса, не удаляя локальные правки.

Атомарный коммит содержит одно логически завершённое изменение. Например, исправление проверки пустого имени и отдельное изменение дизайна интерфейса лучше оформлять двумя коммитами. Так удобнее проводить проверку, искать ошибку и отменять конкретный шаг. Перед сохранением выполняют git status, затем git diff, выбирают нужные изменения через git add и ещё раз просматривают git diff --cached. После git commit -m с понятным сообщением проверяют git log. Если в одном файле были разные правки, git add -p позволяет включить их по частям. Удалённый сервер здесь не обязателен: коммиты создаются локально и отправляются через git push отдельно.

Вывод: git diff позволяет увидеть реальное содержимое изменений, а маленькие осмысленные коммиты делают историю понятной и обратимой.

## Практическое задание. Просмотр карточки заказа

Условие (по скану преподавателя). Заказы Z1 — Новый — Север, Z2 — Готов — Центр, Z3 — Выдан — Юг. Пользователь считается менеджером. По одному артикулу вывести его карточку с тремя полями; неизвестный артикул — «Заказ не найден». Записи не изменять.

### Решение на Python 3

[Открыть код](practice.py). Запуск из корня проекта

```sh
python docs/06/practice.py
```

### Как объяснить код преподавателю

found сначала равен False. Когда артикул совпал, выводим карточку, меняем found на True и завершаем поиск через break. Список не редактируется.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.
