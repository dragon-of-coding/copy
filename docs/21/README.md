## Вопрос 1. Организационные процессы обеспечения проекта и процессы управления проектом

Организационные процессы обеспечения проекта создают условия, необходимые для выполнения работ в организации: управление инфраструктурой, персоналом, компетенциями, знаниями, качеством и общими процессами. Они действуют на уровне компании и поддерживают несколько проектов. Например, организация выбирает систему хранения кода, регламенты безопасности, способы обучения сотрудников и единый подход к аудиту.

Процессы управления конкретным проектом обеспечивают достижение целей в пределах согласованных сроков, бюджета и качества. Они включают планирование, оценку ресурсов, распределение задач, контроль исполнения, управление рисками, изменениями и конфигурацией, принятие решений и информирование заинтересованных сторон. На практике используют календарные планы, backlog, доски задач, реестр рисков, отчёты о статусе и метрики.

Различие уровней: организация обеспечивает единые правила и ресурсы, проект применяет их к конкретному результату. Например, компания предписывает использовать GitLab и обязательные тесты, а команда проекта определяет ветвление, расписание релизов и требования своего CI. Процессы связаны обратной связью: итоги проектов помогают улучшать общие организационные правила.

Организационные процессы создают условия для нескольких проектов: предоставляют инфраструктуру, подбирают сотрудников, поддерживают правила качества, управление знаниями и совершенствование способов работы. Процессы управления конкретным проектом отвечают за его план, бюджет, сроки, риски, задачи и контроль выполнения. Например, организация обеспечивает общий GitLab-сервер и правила резервного копирования, а руководитель проекта планирует, кто и когда подготовит конкретный релиз. Разделение помогает не перепутать долгосрочные возможности предприятия с ежедневным управлением одним продуктом. В обоих случаях результаты должны быть проверяемы: планы, отчёты, перечни рисков, решения и протоколы.

Вывод: организационные процессы отвечают за способность компании регулярно выполнять проекты, а проектные — за успешное выполнение конкретных работ.

## Вопрос 2. Удалённый репозиторий GitLab и маркировка выпуска аннотированной меткой Git

Удалённый репозиторий — хранилище истории Git на сервере, например GitLab. Локальный репозиторий существует независимо от него; связь создают командой git remote add origin URL. Команда git fetch загружает информацию о новых коммитах и ссылках, git pull обычно получает и интегрирует изменения, а git push публикует локальные коммиты и теги при наличии прав.

Тег Git — имя, привязанное к конкретному коммиту. Для выпуска предпочтителен аннотированный тег, содержащий автора, дату и сообщение: git tag -a v1.2.0 -m "Release 1.2.0". Для публикации используют git push origin v1.2.0 или в согласованном процессе git push --tags. Теги помогают найти точные исходники релиза и запустить сборочный pipeline по правилу для CI_COMMIT_TAG.

Перед маркировкой проверяют, что коммит прошёл тесты, собран требуемый артефакт и состав выпуска утверждён. Переписывать и переиспользовать уже опубликованные релизные теги нежелательно: это нарушает воспроизводимость. GitLab Release может дополнительно связать тег с описанием версии и файлами.

Удалённый репозиторий GitLab хранит общую историю и позволяет команде обмениваться коммитами, выполнять CI и обсуждать изменения. Связь с ним настраивают через git remote add origin ..., отправляют ветку командой git push. Аннотированная метка создаётся как git tag -a v1.0.0 -m 'Release 1.0.0'; она указывает на конкретный коммит и содержит собственное сообщение и информацию об авторе. Чтобы коллеги увидели тег, его отдельно отправляют через git push origin v1.0.0. Метка полезна как точка выпуска и источник проверяемой версии при сборке. Сам факт создания тега не гарантирует успешности тестов: перед маркировкой нужно убедиться в качестве релиза.

Вывод: remote обеспечивает совместную работу, а аннотированный тег однозначно отмечает проверенную точку выпуска.

## Практическое задание. Редактирование даты выдачи заказа

Условие (по скану преподавателя). Заказы Z1 — дата 2026-12-01, Z2 — 2026-12-02, Z3 — 2026-12-03. Пользователь — администратор. По артикулу обновить дату в формате ГГГГ-ММ-ДД только при действительной календарной дате; иначе показать ошибку и оставить значение прежним. Использовать стандартные средства работы с датами.

### Как объяснить код преподавателю

Первые проверки требуют запись ровно из десяти символов с дефисами на своих местах. date(год, месяц, день) проверяет календарь, а isoformat() — точный формат с нулями. При ошибке присваивания orders[sku] не происходит.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.
