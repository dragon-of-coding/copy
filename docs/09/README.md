## Вопрос 1. Источники поставки программного обеспечения. Проверка подлинности и целостности файлов

ПО получают с сайта производителя, официального магазина или репозитория пакетов, корпоративного сервера артефактов, из проверенного исходного кода или по договору с поставщиком. Источник должен быть доверенным, а версия — подходящей для целевой системы. Загрузка с неизвестных зеркал и установка неподписанных исполняемых файлов увеличивают риск вредоносного кода и подмены.

Подлинность означает, что продукт действительно выпущен заявленным поставщиком; её подтверждают цифровые подписи, сертификаты издателя и доверенная цепочка поставки. Целостность означает, что содержимое не изменилось: вычисляют криптографический хэш (например SHA-256) и сравнивают с контрольной суммой, опубликованной в доверенном канале. Сам по себе хэш, скачанный с того же взломанного сайта, не гарантирует подлинность.

Дополнительные меры: проверка HTTPS, электронных подписей пакетов, корректности версии и лицензии; анализ состава зависимостей (SBOM), проверка уязвимостей и хранение проверенных артефактов. При развёртывании фиксируют номер версии или digest образа, чтобы можно было точно воспроизвести поставку.

ПО можно получать с официального сайта производителя, из репозитория пакетов, корпоративного каталога или доверенного реестра контейнеров. При выборе источника оценивают его подлинность, поддержку и возможность получения исправлений безопасности. Контрольная сумма SHA-256 подтверждает, что скачанный файл совпадает с эталонным по содержимому, но сама по себе не доказывает, кому он принадлежит: хеш нужно получать из доверенного источника. Цифровая подпись помогает проверить происхождение и неизменность данных при наличии проверенного ключа. Не рекомендуется устанавливать неизвестные сборки с подозрительных сайтов даже при совпадении заявленного названия версии.

Пример: дистрибутив скачан с официального сайта; вычисленный SHA-256 совпал с опубликованным; подпись производителя действительна. Вывод: проверяют не только то, что файл открылся, но и его происхождение и неизменность.

## Вопрос 2. Подготовка версии приложения и состава комплекта развёртывания

Версия приложения — идентифицированное состояние продукта, предназначенное для проверки и поставки. Подготовка включает выбор коммита, актуализацию номера версии, завершение необходимых изменений, выполнение тестов и сборку воспроизводимого артефакта. Часто применяют SemVer (MAJOR.MINOR.PATCH), но конкретная схема зависит от проекта.

Комплект развёртывания включает исполняемый файл, пакет или контейнерный образ; список зависимостей; конфигурационные шаблоны; миграции БД; инструкции установки и обновления; инструкции запуска, проверки и отката; изменения версии (release notes). По ситуации добавляют контрольные суммы, подписи, эксплуатационные инструкции и сведения о лицензировании. Секреты в комплект не включают.

Перед передачей в эксплуатацию выполняют контроль сборки, тестирование на среде, близкой к целевой, проверку совместимости и подлинности. Артефакт привязывают к конкретному коммиту и тегу, чтобы не возникало ситуации «релиз 1.2» с разным содержимым на разных серверах. Приёмщик получает критерии проверки и известные ограничения.

Комплект развёртывания должен быть понятен человеку, который не писал программу. Помимо запускаемого артефакта в него входят номер версии, список изменений, требования к окружению, пример конфигурации без паролей, инструкция установки, проверки и отката. Манифест может перечислять имена и контрольные суммы файлов, чтобы убедиться в полноте передачи. Версию лучше определять заранее и использовать последовательно в Git, сборке и журнале выпуска. Перед передачей проверяют, что артефакт можно установить в чистой среде, а не только на компьютере разработчика, где могут оставаться случайные зависимости.

Вывод: результат подготовки релиза — не просто папка с программой, а однозначно идентифицированный, протестированный и документированный комплект поставки.

## Практическое задание. Добавление нового заказа

Условие (по скану преподавателя). Существуют заказы Z1, Z2, Z3 со статусом «Новый» и пунктом «Центр». Пользователь — администратор. Ввести новый артикул и пункт выдачи; оба поля обязательны, артикул должен быть уникален. Добавить заказ со статусом «Новый», напечатать весь список; при ошибке сохранить записи.

### Решение на Python 3

[Открыть код](practice.py). Запуск из корня проекта

```sh
python docs/09/practice.py
```

### Как объяснить код преподавателю

strip() убирает пробелы по краям, поэтому ввод из одних пробелов считается пустым. Цикл заранее проверяет повтор артикула. append добавляет запись только после всех проверок.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.

### Проверь себя

Ввод: Z2 ↵ Восток   →   Ожидается: Ошибка о повторном артикуле
