## Вопрос 1. Группы процессов жизненного цикла программных средств и их взаимосвязь

Процессы жизненного цикла объединяют в группы по назначению. Для структуры ГОСТ Р ИСО/МЭК 12207-2010 важно понимать процессы соглашения, организационного обеспечения проектов, процессы проекта, технические процессы и специализированные процессы программного обеспечения. В более новых международных редакциях встречается укрупнённая группировка в четыре семейства: соглашения, организационное обеспечение проектов, техническое управление и технические процессы. На экзамене следует ориентироваться прежде всего на названный в билете ГОСТ и не смешивать классификации разных редакций.

Соглашения описывают приобретение и поставку продукта или услуги, обязанности заказчика и исполнителя. Организационное обеспечение создаёт общие ресурсы и правила: инфраструктуру, компетенции, качество, управление знаниями и портфелем. Процессы проекта обеспечивают планирование, контроль, управление рисками, конфигурацией и информацией. Технические процессы формируют и реализуют требования, архитектуру, программные компоненты, интеграцию, проверку, переход к эксплуатации и сопровождение.

Эти процессы не изолированы. Требования задают критерии проектирования и тестирования; управление конфигурацией связывает код, документацию и релиз; управление рисками влияет на проверки безопасности; обращения пользователей приводят к изменениям, затем к новой сборке и развёртыванию. Одни процессы выполняются параллельно и повторяются в нескольких итерациях.

Процессы жизненного цикла связаны через результаты друг друга. Например, разработка получает требования, тестирование проверяет созданное решение, развёртывание передаёт его в эксплуатацию, а сопровождение использует сообщения об ошибках для новых изменений. Организационные процессы обеспечивают людей, инфраструктуру и качество. Процессы управления проектом контролируют планы, сроки, риски и ресурсы. Технические процессы создают и проверяют продукт, а процессы соглашения определяют отношения заказчика и поставщика. На практике процессы могут выполняться параллельно и повторяться: найденный дефект возвращает команду к анализу требований или реализации. Важно отслеживать связи между входами и результатами, а не воспринимать группы как независимые списки.

Пример: пользователь запросил новый фильтр. Управление изменением согласует задачу, разработка изменяет код, тестирование подтверждает результат, CI формирует артефакт, развёртывание устанавливает версию, сопровождение получает инструкцию. Вывод: жизненный цикл — согласованная система процессов, а не только последовательность стадий.

## Вопрос 2. Разработка функции в отдельной ветке Git и слияние изменений с основной веткой

Ветка Git — перемещающийся указатель на последовательность коммитов. Отдельная feature-ветка нужна, чтобы разрабатывать функцию независимо от стабильной основной ветки (main) и проверять изменения до объединения. Создание ветки: git switch main, затем git switch -c feature/search. После редактирования выполняют git add ... и осмысленные git commit.

Перед слиянием разработчик запускает тесты и обновляет информацию о репозитории: git fetch, при необходимости синхронизирует свою ветку с main (через merge или rebase по правилам команды). Затем создаёт merge request в GitLab, где происходят код-ревью и автоматические проверки CI. После одобрения выполняется слияние: обычный merge сохраняет историю веток; squash объединяет её изменения в один коммит; fast-forward возможен, когда история линейна.

Командный пример локального слияния: git switch main, git merge feature/search. Конфликты решают вручную, ориентируясь на смысл кода, затем отмечают исправленные файлы и завершают слияние. После проверки временную ветку можно удалить: git branch -d feature/search.

Ветки Git позволяют разрабатывать новую функцию, не изменяя сразу основную рабочую версию. Обычно выполняют git switch -c feature/search, делают несколько коммитов и затем объединяют результат через merge или запрос на слияние. Перед объединением желательно обновить основную ветку и запустить тесты. Слияние не обязательно означает копирование файлов: Git анализирует общую историю и пытается автоматически объединить различия. Если строки конфликтуют, разработчик должен решить, какой итоговый код правильный. После успешной проверки временную ветку обычно удаляют; это не стирает коммиты, уже вошедшие в историю основной ветки.

Важно: слияние — не просто механическое склеивание файлов; нужно убедиться, что изменения совместимы и проходят тестирование. Вывод: feature-ветка изолирует работу, а merge request делает объединение контролируемым.

## Практическое задание. Выбор направления сортировки

Условие (по скану преподавателя). Товары: кеды — 4 пары, ботинки — 9, сандалии — 1. Одна команда: 1 — сортировка по возрастанию, 2 — по убыванию. Вывести название и остаток; при неверном значении сообщить об ошибке, список не показывать.

### Решение на Python 3

[Открыть код](practice.py). Запуск из корня проекта

```sh
python docs/11/practice.py
```

### Как объяснить код преподавателю

Сначала проверяем команду. При 1 меняем местами записи с нарушенным порядком по возрастанию, при 2 — по убыванию. При ошибке сортировка вообще не начинается.

Важно: это самостоятельная консольная программа; исходные данные хранятся в памяти во время запуска. Для данного билета не нужно создавать базу данных и интерфейс.

### Проверь себя

Ввод: 1   →   Ожидается: сандалии, кеды, ботинки

Ввод: 2   →   Ожидается: ботинки, кеды, сандалии

Ввод: 9   →   Ожидается: Ошибка без отсортированного списка
